Chapter 3: Requirement and Analysis

3.1 Problem Definition

Currently, computer science students frequently struggle to bridge the gap between theoretical classroom learning and practical coding execution. Traditional academic environments often lack real-time, adaptive mentorship systems. When novice programmers encounter syntax errors or logical missteps, they are typically met with raw, unforgiving compiler errors that induce frustration and impede the learning process. Conversely, simple static auto-grading platforms only provide a binary pass/fail result, failing to analyze the student's underlying logic or pedagogical intent. There is a critical missing link for a robust, curriculum-aligned educational platform that can not only securely host and execute student code, but also provide immediate, AI-driven contextual hints that guide the student toward the solution without directly revealing the correct answers.

3.2 Requirement Specification

3.2.1 Functional Requirements

  • Authentication: Secure user registration and login flows differentiating Student and Educator roles using Google OAuth.
  • Assignment Operations: Educators must be able to create, edit, and assign programming tasks dynamically, while students fetch and attempt these assignments in a browser-based IDE.
  • AI Tutoring & Execution: The system must execute code against test cases securely and, upon failure, seamlessly prompt the generative AI (GyanBot) to evaluate the code and return conversational hints.
  • Reporting & Certification: Automated dashboards must track student progress, dynamically generating PDF certificates upon successful milestone completions, alongside Excel-based activity reports.

3.2.2 Non-functional Requirements

  • Scalability: The backend must leverage Node.js to comfortably handle concurrent inbound code execution requests from a full classroom of students simultaneously.
  • Security: Strict Row Level Security (RLS) policies must be enforced at the database level to fiercely protect user privacy and prevent grade tampering.
  • Reliability: Incorporating a robust fallback mechanism (DeepSeek R1) ensures absolute 100% platform uptime even if the primary AI API (Google Gemini) experiences throttling limitations.
  • Performance: Client-side logic in React (Vite) must maintain high responsiveness, guaranteeing UI rendering and code compiling workflows operate without visible latency.

3.3 Planning and Scheduling

3.3.1 Gantt Chart

The project timeline was meticulously structured following an Agile software development lifecycle methodology, divided evenly into multi-week sprints to isolate architectural milestones. The initial phase focused explicitly on Requirements Gathering and UI/UX wireframing for the interactive code editor. Next, intense backend sprint cycles covered database schema design in Supabase followed by RESTful API endpoints in Node.js. Mid-development sprints aggressively tackled the core innovation: integrating the complex prompt engineering required for reliable generative AI evaluation. The final phase was strictly reserved for comprehensive unit testing, deployment staging (via Render and Vercel), and extensive Beta testing within local user groups. A visual Gantt chart tracked strict adherence to these delivery milestones across the academic semester.

3.4 Software and Hardware Requirements

3.4.1 Software Requirements

  • Frontend Framework: React.js bundled via Vite for optimized speed.
  • Backend Environment: Node.js utilizing the Express.js framework.
  • Database Service: Supabase (PostgreSQL implementation).
  • External APIs: Google Gemini API (Primary Model), DeepSeek R1 API (Fallback reasoning model).
  • Client Browser: Modern HTML5 compliant browser (Google Chrome, Mozilla Firefox).

3.4.2 Hardware Requirements

  • Developer Workstation: Multicore processor (Intel i5/AMD Ryzen 5 or higher) with a minimum 8GB RAM for stable full-stack local server hosting.
  • Client Machine: As computation is offloaded to the cloud infrastructure via web APIs, any basic modern computer or tablet with a 2Mbps stable internet connection can seamlessly access the application.

3.5 Feasibility Study

3.5.1 Technical Feasibility

The project architecture rests entirely on highly mature, exceptionally well-documented technology stacks. Incorporating the MERN-inspired stack alongside advanced, well-supported conversational LLM APIs guarantees there are no unpredictable technological blockages. Securely executing unverified user code on shared servers poses standard risks, however utilizing isolated compiler routing elegantly resolves this technical challenge.

3.5.2 Economic Feasibility

  • Hosting and Service Costs (Supabase): Supabase offers a highly generous Free tier that is more than sufficient for the development, testing, and initial deployment phases of this project. This plan natively includes robust PostgreSQL database usage, built-in identity authentication services (Google OAuth), and strict data storage at no cost, up to substantial operational limits.
  • Application Deployment Costs: The React interface runs effortlessly on Vercel's zero-cost hobby tier, while the Node.js API backend is hosted entirely within Render's free web service allocation.
  • Artificial Intelligence Costs: Advanced natural language evaluation fundamentally relies on the free-tier API allocations provided by Google Gemini and OpenRouter (for DeepSeek R1), entirely negating any direct financial overhead during the academic rollout phase.

3.5.3 Operational Feasibility

The platform features an exceptionally shallow learning curve, drastically increasing its operational adoption feasibility among educators and novice programmers. Because it operates cleanly within a web browser—completely eliminating tedious local compiler toolchain configurations—it can be integrated into existing classroom environments instantly with profound ease.

3.6 Fact Finding Technique

3.6.1 Observation

Initial fact-finding fundamentally began with directly observing computing laboratory sessions. It was routinely noted that novice programmers spent exorbitant amounts of time blocked by trivial syntax errors, severely reducing actual algorithm drafting time.

3.6.2 Record Review

Analyzing available historical academic course syllabi and typical exam grade distributions revealed a widespread necessity for structured, progressive coding homework assignments that directly tracked against specific collegiate learning objectives.

3.6.3 Questionnaires

Surveys were widely distributed among peer computer science students. Data overwhelmingly confirmed severe dissatisfaction with existing online judges; users indicated a strong, unfulfilled desire for localized platforms that offered gentle "hints" rather than blunt failure notices.

3.6.4 Interview

Brief informational interviews heavily engaging local computer science faculty members revealed profound fatigue associated with manual code grading. Educators specifically requested an intuitive, unified dashboard capable of tracking granular student success metrics seamlessly.

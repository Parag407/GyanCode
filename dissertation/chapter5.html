Chapter 5: Implementation and Testing

The implementation phase of GyanCode represents the translation of the system's architectural blueprints into a fully functional, cloud-deployed platform. Built upon a modern React + Vite frontend and a Node.js/Express backend, the system leverages Supabase (PostgreSQL) as its primary data layer, thereby removing the need for a self-managed database server. Google Gemini API and OpenRouter (DeepSeek R1 fallback) power all AI-driven features, including code execution simulation, AI hint generation, and the GyanBot tutor. Every component was developed following a modular, component-driven approach that ensures maintainability and future scalability.

The development cycle was structured into three sequential sprints. The first sprint concentrated on authentication, role-based access control, and the core assignment CRUD operations. The second sprint introduced the AI execution engine, the submission pipeline with automatic point rewards, and the educator dashboard analytics. The third and final sprint delivered the certification system, the leaderboard, student progress charts, and the system-wide report export. Throughout all sprints, version control was maintained through Git, and environment-specific configuration was kept separate via .env files, preventing sensitive keys from entering the public repository.

The testing strategy adopted for GyanCode was multi-layered, encompassing unit testing of isolated utility functions, integration testing of API endpoints against the live Supabase instance, and beta testing with actual students and educators. The system was deployed to production early (Vercel for the frontend and Render for the backend) so that real-world network conditions and authentication flows could be validated continuously rather than only at the end of the project. This continuous-deployment model dramatically accelerated the feedback loop and revealed edge cases — particularly around JWT expiry and AI API rate limits — that would have otherwise been difficult to reproduce in a purely local environment.

Row Level Security (RLS) policies enforced at the Supabase PostgreSQL layer ensure that students can only access their own data, educators can view all student submissions, and administrators retain unrestricted access across every table. The is_educator() and is_admin() SQL functions, defined with SECURITY DEFINER, are evaluated server-side for every database call, creating a tamper-proof access control layer independent of frontend logic. Middleware functions (authenticate and authorize) on the Express backend double-validate every incoming request before it reaches a route handler, providing defence-in-depth security.

The culmination of the implementation effort is a platform that is live, accessible through a public URL, and actively used by learners. The following sections detail the specific implementation strategies, code efficiency measures, testing methodologies, modifications made during development, and the formal test cases used to validate system correctness.

5.1 Implementation Approach

GyanCode was implemented using a full-stack JavaScript approach, allowing a single language — and often shared logic — to span both the frontend and backend. The frontend was scaffolded with Vite + React, providing near-instantaneous hot-module replacement during development and an optimised production bundle at deployment time. Routing was handled by React Router v6, and global state was managed by lightweight useState/useEffect hooks, avoiding the overhead of large state-management libraries for a project of this scope.

On the server side, Express.js was chosen for its minimal footprint and rich ecosystem. Each HTTP route is protected by the authenticate middleware, which extracts and validates the Supabase JWT from the Authorization header, and then optionally by authorize(['Admin']) for privileged operations such as managing platform settings or bulk-deleting users. All database mutations bypass the client-side Row Level Security and instead use the supabaseAdmin service-role client, which provides elevated privileges — an intentional design decision that keeps business logic in the server layer rather than exposing it to the browser.

The AI execution engine, located in backend/utils/ai.js, exposes three key functions: simulateExecutionAI for running code against a single input, verifySubmissionAI for batch-testing all test cases and performing semantic logic validation, and generateHint for generating personalised, contextual hints when a student's submission fails. The runAITask wrapper transparently switches between the Gemini API and DeepSeek R1 (via OpenRouter) based on quota availability, ensuring continuous uptime even when primary API limits are reached.

5.2 Coding Details and Efficiency

GyanCode's codebase follows the principle of separation of concerns: UI components in frontend/src/pages/, reusable presentation components in frontend/src/components/, utility helpers in frontend/src/utils/, and all business logic consolidated within backend/server.js and backend/utils/. This structuring minimises coupling and simplifies both testing and future maintenance.

Data fetching is performed through direct REST calls to the Express backend rather than through the Supabase JavaScript client on the frontend. This architectural choice means that all RLS-bypass operations are handled server-side, preventing accidental exposure of the service-role key in browser bundles. Educator and admin dashboards make use of parallel Promise.all patterns where appropriate — for example, simultaneously fetching students and submissions lists — reducing overall page load latency. Pagination and lazy loading are applied on the Assignments page to prevent performance degradation as the assignment library grows.

Chart.js is used for rendering submission trend graphs and success/failure pie charts on the Educator Dashboard and Student Progress pages. Chart instances are destroyed and re-initialised on component unmount to prevent memory leaks, a common pitfall with canvas-based charting libraries in React's Virtual DOM reconciliation model. The reportGenerator.js utility uses the SheetJS (xlsx) library to produce multi-sheet Excel exports of system statistics on demand, supporting the educator's reporting requirements without requiring any server-side file generation.

5.2.1 Code Efficiency

Efficiency in GyanCode is addressed at both the algorithmic and infrastructure level. On the backend, assignment lists are enriched with submission counts in a single post-fetch aggregation rather than issuing one database query per assignment, reducing the number of round-trips from O(n) to O(1) per list request. The leaderboard endpoint similarly computes period-filtered rankings in-memory after fetching a single, appropriately scoped result set from Supabase.

On the frontend, React's useMemo and useCallback hooks are applied to expensive filter/sort operations such as the student search bar on the Admin Panel, preventing redundant re-computations on every render cycle. Suspense-style skeleton loaders are shown while API calls resolve, maintaining perceived responsiveness. Code-splitting via Vite's dynamic import is used for large page components (e.g., AdminPanel and Certificates), reducing the initial bundle size and improving the First Contentful Paint metric.

5.3 Testing Approach

Testing for GyanCode was conducted across three distinct levels: unit testing of discrete utility functions, integration testing of REST API endpoints, and user-centric beta testing with real participants. This stratified approach ensured that defects were caught as close to their origin as possible, minimising the cost of remediation.

Before formal test execution, a test planning phase identified all critical paths — authentication, assignment submission, point increment, automatic certificate issuance, and AI hint generation — as the highest-priority areas for coverage. Edge cases such as expired deadlines, duplicate successful submissions, and AI API failures were explicitly documented and scripted as test scenarios to ensure that the system degraded gracefully in each case rather than throwing unhandled exceptions.

5.3.1 Unit Testing

Unit tests were written for the AI utility module (backend/test-ai.js) and the model availability checker (backend/test-models.js) to verify that prompt construction, response parsing, and fallback switching logic behaved correctly in isolation. Each function was exercised with both valid and invalid inputs — including intentionally malformed code and empty-string edge cases — to confirm robust error handling. The increment_points PostgreSQL function was validated via direct SQL assertions in the Supabase SQL Editor, confirming atomicity and correct accumulation of points across concurrent inserts.

5.3.2 Integration Testing

Integration testing was performed manually using Postman to exercise all 30+ REST endpoints defined in server.js. Each request was sent with a valid JWT obtained from Supabase Auth, and the response payload, HTTP status code, and database state were verified against the expected contract. Three role-specific Postman collections were maintained — one each for Student, Educator, and Admin — ensuring that forbidden endpoints correctly returned 403 Forbidden and that cross-role data leaks were absent. The CORS configuration was validated against both the Vercel production domain and localhost origins.

5.3.4 Beta Testing

Beta testing was conducted with a cohort of students and two educators over a two-week period. Participants were provided with the live production URL and asked to complete a structured task list covering registration, solving at least three assignments, viewing their progress dashboard, and exploring the AI Tutor. A structured feedback form was used to collect usability observations. Key issues surfaced during beta testing included: (1) the code editor on mobile devices requiring a responsive layout adjustment, (2) an ambiguous error message when submitting code after a deadline had passed, and (3) a race condition in the certificate issuance logic when a student solved the threshold assignment twice in rapid succession. All three issues were resolved before the final submission.

5.4 Modification and Improvements

Throughout the iterative development cycle, several significant modifications were made in response to beta feedback, performance profiling, and evolving project requirements. These changes were not scope creep but rather evidence of a responsive, quality-focused development philosophy.

The most impactful modification was the replacement of the original single-test-case submission model with a multi-test-case architecture backed by the test_cases database table. Initially, each assignment stored a single expected_input/expected_output pair directly on the assignments row. Educators quickly identified that this model was insufficient to detect partial solutions or edge-case failures. The updated system allows an unlimited number of test cases per assignment, each of which can be independently marked as hidden, preventing students from hard-coding solutions. The AI verification function (verifySubmissionAI) was enhanced to process all test cases in a single batched prompt and additionally conduct a semantic logic check to detect non-generalisable solutions.

A secondary improvement concerned the AI fallback mechanism. The initial implementation relied exclusively on the Google Gemini API; however, during peak academic hours, the free-tier quota was exhausted frequently, rendering features such as the AI Tutor and code execution unavailable. The runAITask utility was refactored to automatically route requests to DeepSeek R1 via OpenRouter when a Gemini 429 Too Many Requests error is encountered, ensuring continuous availability of AI features.

The authentication flow was substantially redesigned from the initial username/password model. User registration and login were replaced with Google OAuth (via Supabase's third-party provider integration), allowing students and educators to sign in with a single click using their existing Google account — eliminating the need to manage platform-specific passwords altogether. Upon first sign-in through Google, Supabase automatically provisions a user record, and a dedicated /complete-registration endpoint is called to persist additional profile metadata (name, role, department, academic year) that is not supplied by the OAuth provider. Password-based credential management is retained exclusively for the Forgot Password recovery flow, where Supabase Email OTP is used to authenticate the user's identity before allowing a password reset — a deliberate scoping decision that keeps the convenience of social login for daily use while preserving a secure, verified recovery path.
